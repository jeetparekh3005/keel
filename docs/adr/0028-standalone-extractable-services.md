# 0028. Standalone, extractable generated services (polyrepo path)

- **Status:** accepted <!-- proposed | accepted | rejected | deprecated | superseded by ADR-XXXX -->
- **Date:** 2026-11-20
- **Deciders:** keel maintainers

## Context and problem statement

ADR-0011 chose a monorepo "while the platform is young and churning," explicitly leaving
"a clear path to independent ownership/release cadence later." v0.9 (epic #422) opens that
path: a service generated by `keel new` must be usable **standalone** , extracted to its own
repo, it builds, tests, and deploys on its own. Today it cannot. Every generated service
wires itself to keel through three **monorepo-internal** references that only resolve inside
this repo:

1. **keel-core** , `{ workspace = true }` (py), `path = "../../packages/..."` (rust), a
   commit **pseudo-version** (go), `workspace:*` (ts), or a reactor sibling + parent pom (java).
2. **keel-service-base** , the shared Helm **library chart** is referenced as
   `repository: file://../keel-service-base`; and in fact the generator emits **no chart at all**
   with the service (charts are hand-maintained separately under `deploy/charts/`).
3. **the Java parent pom** , `<parent>` via `relativePath ../../pom.xml`.

Extract the directory and all three break. This ADR decides how a generated service becomes a
self-contained, deployable repo without sacrificing the monorepo's atomic-propagation benefit
(ADR-0021: a keel-core change regenerates every reference service in lockstep, byte-identically).

## Decision drivers

- **Standalone-ready output** , `keel new` outside this repo must yield a service that builds,
  tests, and `helm template`s with no monorepo paths and no manual rewiring.
- **Preserve the monorepo dogfood** , the in-repo reference services must stay monorepo-form
  (workspace/path deps, shared `deploy/charts/`) so the byte-identical lockstep guarantee
  (ADR-0021) and atomic keel-core propagation are untouched.
- **One source of truth per concern** , no second, drifting copy of a chart or a dependency
  pin. The anti-drift discipline (ADR-0021, STATUS) applies to charts as much as code.
- **CI-provable before publishing** , the extracted-build guarantee must be demonstrable in CI
  now, before any package is published, using locally-built stand-ins for the registries.

## Considered options

The crux is reconciling two renders of the same template: the **monorepo-form** the reference
services need, and the **standalone-form** a real `keel new` needs. Three ways to get there:

- **A , Post-generation "extract" transform.** Templates stay monorepo-form; a `keel extract`
  step rewrites workspace/path deps to versioned ones, injects a chart, etc. Cons: the rewrite
  logic is a second, fragile description of the dependency graph that must track every template
  change; it is exactly the drift ADR-0021 exists to prevent, one level up.
- **B , Two template sets** (monorepo + standalone). Cons: double maintenance, double drift;
  defeats the single-template dogfood.
- **C , One template, a `standalone` mode toggle.** A Copier boolean (default **monorepo-form**)
  selects, at generation time, workspace-vs-versioned deps, no-chart-vs-generated-chart, and
  inherited-vs-own tool config. The reference dogfood renders with the toggle off (byte-identical
  monorepo-form); a real `keel new` and the extracted-repo CI smoke render with it on. One
  template, one source of truth, both renders covered by CI.

For how the two **unpublished** dependencies resolve standalone (keel-core, keel-service-base),
the parallel question: a published artifact (PyPI/crates.io/npm/Maven/go-proxy for keel-core; an
**OCI Helm registry** , ghcr `oci://` , for keel-service-base), with a **locally-built
stand-in** (wheel / `cargo package` / `npm pack` / `mvn install` to `.m2` / `helm package` +
`go mod replace`) used by CI until publishing (tasks #1-5) lands.

## Decision outcome

Chosen: **Option C , one template with a `standalone` mode toggle**, plus **published
dependencies with locally-built CI stand-ins**.

- **`standalone` Copier variable** (default `false` = monorepo-form). Off: today's behavior
  exactly , workspace/path keel-core, no service chart, inherited tool config; the reference
  services and the ADR-0021 dogfood are **unchanged and still byte-identical**. On: versioned
  keel-core dependency, a generated per-service **application chart** depending on
  keel-service-base, and a self-contained tool config (own `ruff`/`rustfmt`/etc. settings rather
  than inheriting the repo root).
- **Chart generation (standalone-form only).** The template emits a thin application chart
  (`Chart.yaml` + `values.yaml`) that `dependencies:` on **keel-service-base by version from an
  OCI Helm registry** (not `file://`). The monorepo-form render still emits no chart and keeps
  using the hand-maintained `deploy/charts/*` , so no chart migration, no second copy of the
  reference charts.
- **Dependency resolution.** keel-core is consumed by published version per language (tasks
  #1-5); keel-service-base is published to `oci://ghcr.io/jeetparekh3005/keel/charts`; the Java
  parent pom is consumed as a published parent. Until each is published, the **extracted-repo CI
  smoke** builds the artifact locally and points the standalone service at it (wheel install /
  `go mod replace` / path-or-packaged crate / `.m2` install / `helm package` of the library
  chart), so extraction is proven now and the stand-in is swapped for the real registry when
  publishing lands.
- **Extraction is a copy, not a transform.** Because standalone-form is already self-contained,
  "extract" is `cp -r` of the generated directory , no rewrite step to drift (option A rejected).

### Consequences

- **Good:** `keel new --standalone` yields a repo that builds/tests/deploys on its own; the
  monorepo dogfood and atomic propagation are untouched; one template, one source of truth; the
  guarantee is CI-proven before publishing via locally-built stand-ins.
- **Bad:** the template carries conditional (`standalone`) blocks, which are more complex to read
  and must be covered **in both modes** by CI (the non-item jobs cover monorepo-form; new
  extracted-repo jobs cover standalone-form). keel-service-base must be published to an OCI Helm
  registry , a new release artifact to version and sign.
- **Neutral:** this is the concrete "polyrepo path" ADR-0011 deferred; ADR-0011 is updated to
  point here. Task #6 ("generated service depends on the published package") becomes "the
  `standalone` render depends on the published package," and is finished when publishing (tasks
  #1-5) lands and the CI stand-ins are swapped for real versions.

## More information

  ADR-0011's status note is updated to reference this ADR.
- Builds on [ADR-0021](0021-generator-and-propagation.md) (Copier generator + lockstep dogfood) and
  ADR-0009 Tier 3 (keel-service-base library chart).
- Implements v0.9 epic #422 tasks: extracted standalone-repo smoke (generate -> extract ->
  build + test + `helm template`), chart generation, and the `keel new` published-dependency
  switch. Publishing (keel-core per registry + keel-service-base to OCI) is the paired track.
- **Maven coordinate (#422 task 4).** keel-core-java publishes to Maven Central under groupId
  **`io.github.jeetparekh3005`**, not `io.keel`: the project owns no `keel.io` domain, and the
  Sonatype Central Portal auto-verifies a GitHub-based namespace (`io.github.<github-user>`)
  against the GitHub account with no DNS record. Only the Maven **groupId coordinate** changes; the
  Java **package** namespace stays `io.keel.*` (the two are independent). The deploy uses the modern
  Central Portal via `central-publishing-maven-plugin` behind the pom `release` profile
  (`publish-maven.yml`, release-gated, four gated secrets, idempotent). The parent pom carries the
  Central-required metadata (url, licenses, developers, scm) that keel-core inherits.
